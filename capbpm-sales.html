Internal Business Operations Platform

A single Angular 21 application that Capital BPM staff use to run the business side of client engagements—sales pipeline, statements of work, project delivery, time tracking, and reporting—all served by one Spring Boot API with no direct database access from the client.

The Problem

A consultancy lives and dies by the handoff between selling work and delivering it. At Capital BPM that handoff crossed several systems that didn't talk to each other: opportunities lived in Salesforce, hours and project financials lived in a PSA tool, and the connective tissue—statements of work, delivery status, utilization, margin —lived in spreadsheets and inboxes.

The answer was one internal single-page application that spans the whole arc. Sales moves an opportunity through the pipeline, the SOW is built from it, the project is created and staffed, hours land against it, and delivery, utilization, and profitability all report off the same data. Everything the client renders comes from a single Spring Boot API—there is no direct database access from the browser—and much of that data originates in a Salesforce cache the API maintains.

Users Internal staff across sales, delivery, and finance
Consolidates Pipeline, SOWs, projects, and time data previously split across Salesforce, a PSA tool, and spreadsheets
Hard constraint No client-side database access—every read and write goes through the API
Outcome One SPA covering sales through delivery through reporting

Architecture

A domain-restricted sign-in fronts an Angular SPA that holds no data of its own. Every view resolves through the Spring Boot API, which in turn reads from a maintained Salesforce cache and the PSA system rather than hitting those vendors on each request.

What It Does

The app is organized around the life of an engagement. Each area below is a distinct module in the routing tree, but they share the same data table, the same lookup services, and the same API client.

Sales pipeline

  • Pipeline Pulse — a rollup of deals in flight and where they sit in the process
  • Opportunity activity — movement and touchpoints on individual deals
  • Opportunity creation — new deals entered against cached Salesforce accounts

Statements of Work

  • SOW builder — compose and edit a statement of work off a won opportunity
  • SOW library — browse and reuse language from past engagements
  • Export to PDF so the document leaves the app in a client-ready form

Projects

  • Full CRUD module — list, create, edit, and a detail view per project
  • PSA import — pull existing projects in rather than re-keying them
  • Project Visibility — portfolio-wide status and budget performance (see below)

Delivery & resourcing

  • Delivery dashboard — what's in flight and how it's tracking
  • Utilization report — billable share of staff time across the portfolio
  • Resource profiles and a profitability model for margin trends

Time tracking

  • My Hours — individual time entry against projects
  • Hours report pulled from the PSA system
  • Compliance tracking with scheduled escalation email for unlogged time
  • Time-tracking KPIs surfaced alongside delivery reporting

Reporting & tasks

  • Project status reports feeding the visibility notes described below
  • Task tracker for general internal follow-ups
  • Client QA checklists for pre-delivery review
  • Email templates managed in-app and sent through the API

Admin tooling

  • App-wide constants and dropdown values, editable without a deploy
  • Salesforce account to document-folder lookups
  • Automated record-based and scripted test tooling for regression checks

Access model

  • Google OAuth in production, restricted to company domain accounts
  • An admin-access guard fronts every admin route
  • On localhost the app seeds a mock user and skips auth entirely, so local development needs no live credentials

Spotlight: Project Visibility

The feature I spent most of my time on answers a question leadership was asking constantly and couldn't answer quickly: across the whole portfolio, which projects are healthy and which are burning budget faster than they're delivering? The data existed—it was scattered across status reports, the PSA system, and people's heads.

Project Visibility is a portfolio-wide panel that puts status and budget performance for every active project in one grid. I wired the detail pane to real status-report data rather than the placeholder it started on, then added editable free-text notes with last-edited-by attribution, so a delivery lead can leave context on a project and everyone can see who said it and when. I also added import and delete actions to the panel so the portfolio could be curated without a round trip to an admin.

The work that took longest was the least visible. Change detection had to run inside Angular's zone for state updates arriving from outside it, or edits would land in the model and never reach the screen. And the shared date formatter silently mangled ISO datetime strings—fine for a plain yyyy-MM-dd, wrong the moment a timestamp carried a time component—which meant every "last updated" in the panel displayed incorrectly until it was fixed at the utility level.

Engineering Conventions

An internal app that grows for years gets inconsistent unless the rules are explicit. These are enforced in review, and following them is most of what made a three-month ramp-up productive.

#ConventionWhy it exists
1 One shared data-table component Every real data grid goes through <app-data-table>. Sortable, resizable, reorderable columns, Excel export, row counts, and cookie-persisted layout come free everywhere. Raw <table> markup for data is disallowed.
2 Typeahead over long dropdowns Any dropdown past roughly ten options becomes a typeahead with case-insensitive substring matching, backed by a preloaded and cached service—never a per-keystroke API call.
3 Dates always render yyyy/MM/dd Formatted manually rather than through locale-dependent Intl or toLocaleDateString, so the same record reads identically for every user regardless of browser locale.
4 Modern Angular throughout Standalone components, signals for state, and the @if / @for control flow. No NgModules and no legacy structural directives in new code.
5 Feature branch, PR, squash merge No direct pushes to main. A merged PR builds and pushes a Docker image to the container registry, so what ships is always what was reviewed.
